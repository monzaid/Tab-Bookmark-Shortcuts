## 0. 本层对上游决策的修订

### 0.1 G5 精细化（G5-refined）

**原 G5**：文件驱动 + **一个全局**显式「清空」指令。

**修订为**：**每维度一个「增量 / 覆盖」模式** —— "覆盖"即该维度的"清空指令"，只是不再全局化。

**依据**：用户方案（2026-10-05）。全局开关**无法表达**"槽位覆盖、规则保留"这类组合，而该组合是真实诉求。

**含义**：C4 要求的「文件 + 意图」中，"意图"从此有确定形状（**每维度一个模式**），服务端可完全重算 —— 因此 **A1 的"包自描述"不再需要 manifest**。

### 0.2 G4-C（可逆）撤回的架构后果

见 Constraint 层 §0.3。本层的三条衍生决策随之作废：

| 原决策 | 状态 |
|---|---|
| ~~撤销快照保护被清空图标（改名 vs 复制）~~ | **作废** |
| ~~快照可行性探测（预览阶段算体积 + 查配额）~~ | **作废** |

## 1. 交叉发现的技术现实（非选择题，必须接受）

### 1.1 跨存储区无事务

C10-② 要求「清空图标键与写入配置**同属一次原子操作**」，但 **`storage.sync` 与 `storage.local` 是两个独立存储区，没有跨区事务**。

「原子」只能靠**顺序 + 补偿**近似：

```
① 改/删 local 图标键  →  ② 写 sync 配置
② 失败 → 补偿：改回/恢复 local 键
```

补偿期间若 service worker 被挂起（MV3 常态），会留下**不一致窗口**。

**含义**：C3 的"配置零改动"要靠**补偿路径**兑现，而非免费获得；补偿路径**只在失败时执行**，因此必须被主动测试（见 A13）。

### 1.2 配方渲染需要 canvas

A6 让链路侧要求 data URI，而 `renderIconToDataUri` **同步创建 canvas**，`getSyncState()` 是高频调用。

**含义（A6 的派生要求）**：必须**真用** `iconResolutionCache` 记忆化，不能每次读取都重渲染。既有 `local-icon:` 解析走的正是这条路。

## 2. 决策记录

### A1 — 包自描述：缺失即权威 + 按维度显式模式

**决策**：不设 manifest。**缺失由存在性表达**，其含义由**按维度显式选择的模式**决定：

| 情形 | 增量导入（**默认**） | 覆盖导入 |
|---|---|---|
| **文件缺失、目标机有** | **保留**目标机（例：slot 4 / rule 9） | **删除**目标机 |
| **文件有、目标机有** | **由 diff 决定**（用户确认保留/覆盖） | **同左** —— 同样由 diff 决定 |
| **文件有、目标机无** | 新增（**也展示在 diff**） | 新增 |

> **更正（2026-10-05）**：模式**只管辖「文件缺失、目标机有」**这一种情形；「双侧都有」由 **diff 确认**，两种模式**行为相同**。初稿曾把"以文件为准"当作双侧情形的通则，属错误简化。
>
> 由此：**"增量"不等于"不删除任何东西"** —— 是否删除由**最终 diff 结果**决定（逐记录覆盖可把某行改为删除），不由模式名决定。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| manifest（包内显式清单） | G5-refined 后意图已显式，清单属冗余；且需维护"清单与内容一致"的第二重校验 |
| 类型化缺失（`null`/`[]`/absent 三态约定） | JSON 中极易写错，而 C8 的宽容读取会**掩盖**这类错误（与 G4-A 保真方向相反） |

**含义**

- 解决了"`缺失` 一词被重载"的歧义：含义不再由意图**推断**，而是由用户**明确声明**。
- 按维度建模还带来一处**更好的默认**：覆盖导入是高风险操作，而**默认落在保留**（增量），无需用户先学会"什么不该动"。

### A2 — 文件未承载的维度

**决策**（用户原话）：**不提供选择器** —— UI 标注"本包未包含规则"，该维度**按增量处理**（保留目标机），**不给出删除入口**。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 照覆盖执行（删除目标机该维度全部） | 一次误选即全毁；且这类删除**无法被 diff 行项充分表达**（它删掉的是文件里根本不存在的记录），与 C3「预检通过才提交」精神相悖 |
| 提供选择器但"覆盖"需二次确认 | 用户选择更彻底的做法：直接不给入口 |

**含义**：把"我想用一份干净包重置规则"的表达**限制在合法路径**上 —— 若要清空某维度，必须由**携带该维度**的包表达。

---

### A3 — 三态由 JSON 自身表达

**决策**（用户原话）：**未携带的维度其字段结构不存在；已携带但为空的维度其字段是空数组**（如 `[]`）。维度数据为空时**仍提供**增量（默认）/ 覆盖选择。

| 文件中的形态 | 含义 | UI | 模式选择 |
|---|---|---|---|
| 字段**不存在** | 维度**未携带** | 标注"本包未包含规则" | **不提供**（按增量） |
| `[]` | 已携带但为空 | 正常 | **提供** |
| `[...]` | 已携带有记录 | 正常 | **提供** |

**价值**：三态**由 JSON 语法天然区分**，不需要额外清单，也不会像 `null`/`[]`/absent 约定那样容易被误写。

**派生**：非数组维度（`matchSettings` / `switchDirection` / `autoBindGlobal`）**只有两态** —— "空"无写法，故只有「未携带 / 已携带」。

---

### A4 — 文件与目标机都有的记录

**决策**（用户原话）：**逐维度模式为默认值，逐记录可覆盖** —— 提供 diff 功能，预览表每行可单独改（"这条保留目标机"），**未改动者继承所属维度的模式**。

> **更正（2026-10-05）**：逐记录决策按 A1 更正后的定义，**管辖「文件缺失、目标机有」**（保留 / 删除）；「双侧都有」一律由 diff 确认保留或覆盖。

**无需修订设计权威**：既有 `detail-ui-validation-design.md:58` 要求「逐项选择保留现有或采用导入」+「一键全选任一方向」—— 本决策正是它的推广（逐维模式 = 按维度的一键默认）。

**对 C4 的影响**：提交时的意图载荷 = **各维度模式（每维 1 值）+ 稀疏的记录级覆盖（仅用户改过的那些）**。有界，服务端可完全重算。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 文件一律胜出（维度模式为唯一输入） | **与既有设计要求冲突**（:58 明确要求逐项选择） |
| 逐记录决策为准（维度模式仅为批量设置） | 会弱化"按维度表达意图"这一 A1 的基础 |

### A5 — 预览即合同的强制手段

**决策**：**不做比对** —— 信任 UI 重新读取的是同一文件。

**如实记录影响范围**

| 项 | 状态 |
|---|---|
| C4「服务端重新推导」 | **不受影响** —— 服务端写的始终是**当前文件**的内容，而非 UI 声称的内容。权威性未削弱 |
| G4-B「预览即合同」 | **作用域收窄** —— 配置漂移由 C3 版本号兜住；**文件漂移不再校验** |
| 残余风险 | 用户在预览后于磁盘上改了该 JSON → 会静默得到与预览不同的导入 |

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 文件指纹（几十字节摘要） | 用户判断实践中几乎总成立 |
| 全量结果比对 | 重复一次确定性推导；载荷随记录数线性膨胀 |

**📐 待决**：是否至少在提交前**重读一次文件**（成本更低，不属"比对"）。

> **已解决（2026-10-05，📐 层 A15）**：该残余风险被**构造性消除**，而非"接受不检测"。UI **复用 `INSPECT` 时读到的那一份字符串**传给 `APPLY` → 预览内容与写入内容在构造上同一 → **无需比对、无需指纹、无需重读**，漂移不可能发生。判据 B 由此从"通常成立"升为**结构保证**。本项待决随之关闭。

### A6 — 配方型图标的值模型

**决策**：**配方只存在于存储层，链路解析时渲染** —— `IconSource` 用 `type:'template'` + 配方字段承载；链路一侧仍只看到 **data URI 字符串**（经 `renderIconToDataUri` 渲染，复用 `iconResolutionCache` 记忆化）。**链路值模型零改动**。

> **⚠️ 渲染落点最终裁定（2026-10-05，用户裁定 R1）**：**渲染统一在 background，使用 `OffscreenCanvas` 产出 PNG。**
>
> **决策过程（含一处必须先纠正的错误）**
>
> - **Q1=A（UI 侧渲染）已被 R1 取代。** 其依据是错误的：我曾写"background 无 canvas"，指的是 `document.createElement('canvas')`（在 service worker 中确实不可用）；但 **`OffscreenCanvas` 是 MV3 service worker 可用的平台 API**（Chromium 与 Firefox 均可），**无需新增任何依赖**。
> - Q1=B 之所以当时被否决，正是因为它被归入"需引入编码依赖"；该归因同样错误（`OffscreenCanvas` 是平台内建）。
>
> **R1 的决定性理由：投递路径根本不经过 UI**
>
> ```
> 31:33:src/background/apply-fields.ts
>     if (typeof favicon === 'string') {
>       // Last line of defence (B9). Serialized into the page context, so the
>       // allowlist is mirrored inline and must stay semantically identical to
>       // `isSafeFaviconProtocol` (http/https, or data: limited to bitmaps).
> ```
>
> 页面图标的真正生效由**内容脚本的导航事件**驱动 —— **那时没有任何 UI 页面存在**；`apply-fields.ts` 在页面上下文执行，只接受**字符串**，且其 `isSafeFavicon`（`:48-62`）在 `:71` 处**拒绝 `image/svg+xml`**。
>
> → **"UI 侧渲染"只能修好 UI 可见面**（侧边栏预览、设置页），**修不好"页面图标真正生效"**。若采用 UI 侧渲染，投递侧仍需一个渲染器 → **两个渲染器并存**，正是本文档已否决过的那类风险。
>
> **R1 的形态**：background 以 `OffscreenCanvas` 把配方渲染为 **PNG data URI**（可通过 `isSafeFaviconProtocol`），UI 与投递路径**共用同一渲染结果**（经 `iconResolutionCache` 记忆化）。
>
> **刻意不选的两个方案**
>
> | 方案 | 否决理由 |
> |---|---|
> | R2 = UI 侧渲染 + 投递侧另作处理 | 必然产生**两个渲染器**，且 UI 不参与投递时无法渲染 |
> | R3 = 投递时把配方交给内容脚本渲染 | 页面上下文保真度虽最高，但会让内容脚本从"接收最小改写指令"变成"模板渲染器"，与设计取向相悖 |
>
> **⚠️ R1 的风险（已知，须 spike 验证）**：service worker 内的**字体 / emoji 保真度**不确定。失败时的降级为**占位**（不得降级为 SVG —— 会被闸门丢弃）。
>
> **不变的部分**：配方仍是**唯一持久真源**；链路值仍只承载 data URI 字符串；**链路值模型依旧零改动**。

> **🔴 R2 —— 渲染落点最终形态（2026-10-05，实施期发现 BLOCKER 后裁定）**
>
> **R1 说对了一半，但落点错了。** 执行期由实现方与独立审查方**各自独立**发现同一 BLOCKER：
>
> ```
> resolveForDisplay（icon-service.ts:413）：生产调用点 = 0（仅测试调用）
> RecipeRenderer：仅被 IconService 内部实例化
> ```
>
> → R1 把渲染器放进了 background（**这一点正确**），但落点是 `resolveForDisplay` —— 而它**没有任何生产调用者**，故"UI 与投递共用渲染结果"**从未成立**。用户保存 Custom Icon 后：**页面图标不生效，UI 也不显示**。
>
> **根因（本设计的一处错误，须显式记录）**
>
> A6 的「链路值模型零改动」**成立**，但我由它推出的落点是错的：`ChainResult` 只承载 `value: string | null`，**`IconSource`（含 `type` 与配方）在进入链路时就被剥离**（证据：`field-chain.ts:112-122` 的 `asSetFavicon` —— `asSet('')` → `null`，故配方**恒为 `null`**；`:168-174` slot 层 `''.trim()` falsy 亦跳过；`field-delivery-service.ts:233` 仅 `winner.value !== null` 才 `set`）。且渲染是 **async**，`field-chain` 是**同步纯函数**。
>
> ∴ **配方必须在"进链之前"就被物化成 `value`** —— 这正是 A6 决策句原文「链路解析时渲染」的本意；Q1=A 与 R1 的实现解读都偏离了它。
>
> **R2 的形态：渲染落点 = `resolveIconReferences`（读取时物化）**
>
> 在 `storage-repository.ts` 的 `resolveIconReferences(state)` 中对 `icon.type === 'template'`：
>
> 1. 调用 `RecipeRenderer.renderToPng(recipe)`（复用已落盘渲染器 + `iconResolutionCache` 记忆化）；
> 2. 把 **PNG data URI 写入 `value`**；
> 3. **配方字段（`backgroundColor` / `text` / `textColor`）原样保留**；
> 4. **`type` 保持 `'template'`**（不得改写 —— 否则 UI/导出丢失"这是配方"这一事实）。
>
> 读取后的形态：`{ type:'template', value:'<data:image/png;base64,…>', backgroundColor, text, textColor }`
>
> **为何此处是正确落点（决定性事实）**
>
> - `field-delivery-service.ts:195-197` 已是 `const sync = await this.repo.getSyncState();` —— **async 障碍不存在**；
> - `resolveIconReferences` **已在做同形状的"解析时物化"**：把 `local-icon:` 引用解析为真实 data URI（**现成先例，非新范式**）；
> - 投递与 UI **都**经 `getSyncState()` 取数 ⇒ 在此渲染即**天然共用同一结果**，R1 的承诺自动达成。
>
> **三条同时成立**
>
> | 需求 | 满足方式 |
> |---|---|
> | 链路可用 | 链路只读 `value` → 得到 PNG，过 `isSafeFaviconProtocol` ⇒ **A6「链路值模型零改动」得以保全** |
> | 投递生效 | 投递同走 `getSyncState()` → 得到 PNG |
> | UI 可编辑 + 导出可复现 | UI / 导出读**未被覆盖的配方字段** |
>
> **⚠️ 两条硬要求**
>
> 1. **渲染失败的降级必须产 PNG 占位，`value` 中不得出现 SVG。** 独立审查指出：`getPlaceholder()` 产 `data:image/svg+xml`，而投递侧白名单（`src/content/index.ts:172-181,262`、`apply-fields.ts:38-47,71`）**拒绝 `svg+xml`** ⇒ 塞 SVG 会被**静默丢弃**，用户无法区分"没设图标"与"渲染失败"。替代：产 PNG 占位，或留 `value:null` 让其按"未设置"处理并走 `restore`。
> 2. **不得在 `resolveIconReferences` 中改写 `type`**（见上第 4 点）。
>
> **R1 的已知风险已被实测排除**（真实 MV3 service worker，打包后 `sw.js` 内实测）：`hasOffscreenCanvas:"function"`、scope=`ServiceWorkerGlobalScope`；**ASCII 614px / CJK 930px opaque / emoji 3044px、彩色像素 651、9 色** —— **字体与 emoji 保真度实测通过**；产出 `data:image/png;base64,iVBORw0K`（PNG magic 正确）；0 尺寸 canvas 抛 `IndexSizeError` → catch → 落占位（降级路径确被触发过）。

> **🔗 R2 的落点同时是 C9-②（缺失判定）的正确落点（实施期发现，2026-10-05）**
>
> 独立审查发现：`resolveIconReferences`（`storage-repository.ts:418` / `:429`）在引用**解析失败**时执行 `if (actualUri)` —— 失败则**原样保留 `local-icon:…` 字面量**，该字面量随后流到 `src/ui/sidebar/App.tsx:490` 的 `<img src={displayIcon}>` → **破图**（既有静默降级缺陷）。
>
> 而同期新增的 `resolveForDisplayState` / `isMissingIcon`（`icon-service.ts:461-481`）**无生产调用者** —— 与 BLOCKER 完全同构：**能力就位、接线缺失**。
>
> ∴ **两处修订落在同一个函数**：
>
> | 目标 | 在 `resolveIconReferences` 中 |
> |---|---|
> | 配方投递（R2） | `type === 'template'` → 渲染 PNG 写入 `value`，配方字段与 `type` 保留 |
> | 缺失判定（C9-②） | 引用**解析失败** → **不再原样保留字面量**；按 C9「裸引用 + 一次性告知」置为不可用，并**记录到缺失清单** |
>
> **缺失清单的生产者**：`src/shared/types.ts:372` 已声明 `ImportApplyResult.missingIcons`，但**全 `src/` 无任何填充点** ⇒ 设计 §4.3 承诺的"缺失图标清单 + 修复入口"目前**无实现**。须在此处补上生产者，并由 UI 消费（显示占位 + 行内修复入口，D9）。
>
> **UI 侧接线**：`sidebar/App.tsx` 与 `settings/App.tsx` 现直接读 `.value`（`:490` / `:1997` / `:2428` / `:2519` / `:2526`），无法区分"引用缺失"与"真实图标"。须改为经缺失判定后再渲染占位。

> **🛡️ R2 的必要配套：派生值不得回写持久化（实施期发现并修复，2026-10-05）**
>
> **缺陷**：`writeSync` 与 `mutateSync` 都 `await this.getSyncState()` —— 而该调用**已把配方 `value` 物化为 PNG**，随后整份对象被**持久化** ⇒ **读取时的渲染结果静默变成持久真源**。
>
> **为何必须修**：这正是 A6 明确否决的替代方案（"存储层同时保存配方 + 首次渲染结果"，否决理由：两份状态会漂移 → 静默投递旧图标）；且 PNG 若超 6KB 会被 `offloadLargeIcons` 转存，**膨胀 sync 存储**。
>
> **修法**：新增 `stripDerivedRecipeValues(state)`，在持久化前把 `type:'template'` 的 `value` 归一化回 `''`（**配方字段与 `type` 不动**）。已覆盖两条写入路径：
>
> | 路径 | 位置 |
> |---|---|
> | `mutateSync` | `storage-repository.ts:318` |
> | `writeSync` | `storage-repository.ts:684` |
>
> 二者都位于 `configVersion` 递增与 `offloadLargeIcons` **之前**。
>
> **不改变任何合法写入语义**：合法配方写入本就带 `value:''`，此步只**关闭回写通道**。
>
> **附带确立的不变量**：`type:'template'` 的 `value` **只在读取路径上非空**（读取时物化），**在持久化态恒为 `''`**。代码中以 `type === 'template' && value !== ''` 作守卫。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 链路值扩展为可携带配方（联合类型） | `MaskedSummary` 把 `node.value` **当文本渲染**，联合类型会让该处直接显示成一坨对象 |
| 存储层同时保存配方 + 首次渲染结果 | 两份状态一旦不一致（改了配方、缓存没更新）会**静默投递旧图标** |

**派生要求**：必须**真用** `iconResolutionCache`（见 §1.2）。

**依据（支持本决策的既有事实）**

- `IconSource` 已有 `type:'template'` 与 `backgroundColor` / `text`，**只差 `textColor`**；
- `iconResolutionCache` 已存在，且 `local-icon:` 走的正是"解析后才给链路用"的同一条路。

### A9 — 不可逆导入的替代保障

**决策**（用户原话）：**量化破坏范围 + 提供「导出备份」按钮 + 「我了解风险，确认导入」按钮**，由用户自行选择是否需要备份。

**与 A8 撤回的对抗**

| 要素 | 内容 |
|---|---|
| 量化 | 破坏范围写进提示（"将删除 3 个槽位、9 条规则，且不可撤销"） |
| 按钮一 | 「导出备份」—— 把当前状态固化到磁盘，**可选** |
| 按钮二 | 「我了解风险，确认导入」—— 用户自行选择是否需要先备份 |

**为何优于"强制备份"**：强制备份会伤害最常用场景（拿干净包重置配置），且会把责任外推（多数人会无脑勾选通过），实际保护力低于看起来的样子；**把备份做成按钮**后，它从"仪式"变成"能力"。

**两条派生（📐 落实）**

1. **按钮二承载责任转移，不承载"我已备份"** —— 两者是**并列选择**，不是一个前置条件。若"点了备份即自动放行"，会把备份变成隐性必填，退回强制备份的缺陷。
2. **须说明备份反映的是导出那一刻的状态** —— 用户可能在导出后继续改动配置，避免误以为它总能精确还原当前状态。

### A11 — 动作集合

**决策**：**三动作，各一语义**

| 动作 | 语义 | 写入 |
|---|---|---|
| `EXPORT_PACKAGE(scope)` | 按范围产出包 | 否 |
| `IMPORT_INSPECT(file)` | 解析文件 + 与现状比对 → diff | **否（只读）** |
| `IMPORT_APPLY(file, intent)` | 依意图应用 | **是（唯一写入者）** |

**关键性质**：`INSPECT` **意图无关**（预览是「文件」的纯函数）→ 改维度模式或改单行决策**无需重新 inspect**，UI 只需重渲染；也使它可幂等重跑。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 四动作（+ `EXPORT_DESCRIBE`） | **YAGNI** —— 范围选择器所需的"有哪些槽位/规则"UI 已从 `GET_STATE` 获得；而"导出预览"= 调用 `EXPORT_PACKAGE` 后先展示、后下载，不必单设动作 |
| 两动作（用 `dryRun` 标志区分） | 把"只读推导"与"破坏性写入"混在同一入口 —— 二者在权限、可重入性与心理模型上都不同类，每个调用点都要先确认"这次是不是 dryRun" |

**与备份的关系**：「导出备份」**不需要新动作** —— 它就是 `EXPORT_PACKAGE`（导出的正是当前状态），复用可避免两条语义相同的导出路径各自漂移。

### A12 — diff 行项粒度

**决策**：**记录级为默认，字段级可展开** —— 默认一行一记录（可扫读）；展开后看到该记录内 `title` / `icon` 各自的变化（"标题：A → B""图标：不变"）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 记录级（只标替换/保留/删除/新增） | **不足以支撑裁决** —— 逐记录覆盖的决策依据正是"哪个字段会变" |
| 字段级为默认 | 10 槽位 × 2 + 9 规则 × 2 = 38 行，多数是"不变"，重点被噪声淹没 |

**一致性**：与既有 `MaskedSummary` 的"前 N 条 + …and N more 展开"同一手法，不引入新的交互范式。

### A13 — 测试策略

**决策**：**分层，按"可确定性"划分**

| 层 | 覆盖 |
|---|---|
| **单元测试** | 纯逻辑：包解析 / 校验 / diff / 意图应用 / 配方序列化 |
| **集成测试** | 跨存储顺序与**补偿路径**（**注入 adapter 失败以强制走补偿**） |
| **手工 + `ui-smoke`** | canvas 渲染与真实浏览器行为 |

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 以集成测试为主 | 自然流向只走成功路径，而**成功路径恰恰是最不需要保护的一半** —— 关键不是"多集成"，而是**能制造失败** |
| 引入真实浏览器 E2E 覆盖全流程 | canvas 确实只能在真实浏览器验证，但把整条链路拖进 E2E 成本过高 |

**一致性**：与仓库既有 `unit / integration / ui-smoke` 三层**同名同形**，不新增测试范式。

### A14 — 包的 schema 与内部形态的关系

**决策**：**独立的传输 schema**

```
{
  schemaVersion,
  exportedAt,
  scope,
  slots?,      // 显式的可携带记录
  rules?,
  settings?
}
```

每条记录是**显式的可携带记录**（只列该携带的字段）。需**双向映射层**（`SyncState ⇄ 包`）。

**关键前提（本决策的必要性）**：包**不可能**照抄内部 `SyncState` —— 导出时图标已被改写（URL / 裸引用 / **配方对象**），而配置里那份是 data URI 字符串。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 镜像内部形态（顶层与记录都沿用 SyncState 形状） | 内部字段会**泄漏**进文件（`createdAt` / `updatedAt` / `configVersion` 等），而这些泄漏字段在 C8 下还必须被**逐项披露为"未知字段"** —— 要么污染预览，要么把内部结构写进协议 |
| 顶层独立、记录镜像 | 保留 A 的泄漏问题，只分了一半 |

**另一条支持理由**：G4-A 要求"不改动未勾选的记录"。显式 schema 让"携带了什么"成为**枚举事实**；镜像形态下"没被改动的字段"与"未被携带的字段"在文件里**长得一样**（A1 那条"缺失歧义"在记录内部的翻版）。

**代价（如实记录）**：双向映射层是实打实的代码量，且**记录字段变化时映射需同步维护**。鉴于不背兼容（无需兼容旧文件）+ 选择重构协议（愿为语义投资），这笔成本换来一份**可读、可验证、与内部解耦**的包。

```
导出

导入

                │ 解析 + 严格结构校验 + C8 宽容项收集
                │ 与目标机现状比对 → diff（记录级 + 字段级）
                └─► diff + 各维度"是否携带" + 宽容项清单
                        │
                        ▼
              用户按维度选模式（默认增量）+ 逐记录覆盖 + 确认宽容项

                        ▼

                        ▼

                        │
                        ▼
   IMPORT_APPLY(file, intent)               [唯一写入者]
      │ ① 服务端重算 diff（C4），与 INSPECT 结果比对（A5：不比对文件）
      │ ② 预检全部通过？（C3）── 否 ──► 整体拒绝 + 定位原因 + 化解建议

                        ▼
        提交前重读文件？（A5 遗留，📐 待决）
```

## 4. 错误处理（由 C3 / C4 / C6 / C8 推导）

| 情形 | 处置 |
|---|---|
| 结构性错误（非对象 / 缺关键数组） | 整体拒绝（C8） |
| 版本不符 | **严格拒绝**（G1；C8 的宽容**不适用**） |
| 未知字段 / 缺可选字段 | 宽容读取，但**逐项披露**并要求确认（C8） |
| 记录非法（如不安全正则） | 整体拒绝 + 定位 + 化解建议（C3） |
| 配额不足 | 整体拒绝 + 化解建议（如"减少勾选范围"）（C3） |
| 版本冲突（`STALE_VERSION`） | 整体拒绝（C3，绑定预览版本号） |
| sync 写入失败 | 补偿回滚 local 图标键改动（§1.1） |
| 上传类图标引用不可解析 | 视为"缺失" → 占位 + 清单告知一次（C9） |
| 文件在预览后被改动 | **不检测**（A5） |

## 5. 本层结论摘要

| 编号 | 项 | 决策 |
|---|---|---|
| A1 | 包自描述 | 缺失即权威 + 按维度显式模式（默认增量）；无 manifest |
| A2 | 未携带的维度 | 不提供选择器，按增量 |
| A3 | 三态表达 | `字段不存在` vs `[]` vs `[...]` |
| A4 | 双侧都有的记录 | 逐维默认 + 逐记录覆盖 + diff |
| A5 | 合同强制 | 不做比对（文件漂移不校验） |
| A6 | 配方值模型 | 存储层承载，链路渲染，链路零改动 |
| ~~A7~~ | ~~快照保护图标~~ | **作废** |
| A8 | 导入撤销 | **不实现** |
| A9 | 替代保障 | 量化 + 导出备份按钮 + 风险确认按钮 |
| A10 | 协议 | 重新设计 |
| A11 | 动作集合 | 三动作，仅 APPLY 写入 |
| A12 | diff 粒度 | 记录级默认 + 字段级展开 |
| A13 | 测试策略 | 分层（含注入失败测补偿） |
| A14 | 包 schema | 独立传输 schema + 双向映射层 |

**一句话**：导出产出一份**独立于内部存储的、只带可复现图标信息的传输包**；导入由 `INSPECT`（只读、意图无关）产出**记录级 + 可展开字段级**的 diff，用户按**维度选模式**（默认增量）并可**逐记录覆盖**，`APPLY` 作为唯一写入者在**绑定版本号**上原子写入，失败即**零改动 + 补偿回滚**；不提供撤销，破坏性导入以**量化提示 + 可选备份**替代。
