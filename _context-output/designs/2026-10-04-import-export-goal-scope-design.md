## 1. 基线：本次迭代为何启动

对现有实现的侦察发现 4 项缺陷，其中 2 项会**静默损坏用户数据**。

| # | 发现 | 证据 | 性质 |
|---|---|---|---|
| F1 | 设计要求的「逐槽位冲突表」未接线，设置页只有两个单选按钮 | 设计 `detail-ui-validation-design.md:58`；`ImportPreviewTable` 完整存在于 `src/ui/import-preview/App.tsx`，但全仓无引用（仅 `vite.config.ts:36` 打进入口） | 功能缺失 |
| F2 | **「Keep existing (merge)」名不副实，且静默丢弃全部规则** | `commitImport` 中 `state.rules = preview.rules` 无条件整体替换；UI 该模式下所有冲突槽位一律 `decision: 'existing'` | **数据损坏** |
| F3 | 本地图标导出为 `[local:xxx]` 占位，界面全程不提示 | `import-export-service.ts:49` 做替换；设计 `constraints-permissions-privacy-design.md:41` 要求提示，UI 侧缺失 | **静默降级** |
| F4 | 导入路径的并发保护形同虚设 | UI 发 `IMPORT_COMMIT` 不带 `configVersion`（`settings/App.tsx:2073`）；后端 `?? this.repo.getConfigVersion()`（`worker-orchestrator.ts:756`）取当前版本 → `writeSync` 乐观锁必然通过 | 一致性缺口 |

另有一项**既有设计未被满足**：`import-merge` 决策（`decisions.yaml:331`）要求"完全替换或合并导入；合并时槽位冲突逐项选择"，当前实现只做到"全选任一方向"。

## 2. 决策记录

### G1 — 迭代目标

**决策**：**B + C 并做**（修正错误语义 + 扩展能力），且**不承担向后兼容**。

- 背景：用户明确处于开发阶段，无历史包需要兼容。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 仅对齐设计权威 | 只补一块已有砖，不修 F2/F3 这类会损坏数据的语义 |
| B only | 会让"分享单条规则/槽位"名不副实 |
| C only | 在 F2 未修的前提下，扩展只会放大静默损坏面 |

**含义（不兼容所解锁的简化）**

- `version !== 1` 的 legacy 判别分支（`service.ts:90`、Ruling 4）可去掉 → 只留"严格校验当前 schema"。
- `switchDirection === 'previous' ? … : 'next'` 的静默纠正（`service.ts:153`）→ 改为**严格拒绝**非法值。
- `siteSnapshot?` 可选、`configVersion ?? 0` 之类宽容读取可**收紧为必填**。

> 上述三条当前都属于"宽容读取"，会把**文件损坏**误判为**正常导入**并静默改写用户配置，与 G3 的判据 B 反向。

---

### G2 — 传送模型（包形态）

**决策**：**B — 一个版本化的「可携带包」，全量与子集同构。**

同一个 schema；导出时可勾选范围（全部 / 某个规则 / 某个槽位 / 策略）；导入时按"文件里有什么就合并什么"处理。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 仍是全量快照，只修语义 | C 会变成补丁（规则要不要带？带几条？），需要额外定义 |
| C. 拆成"备份"与"分享"两种产物 | 两套 schema、两套校验、两套测试；同一件事定义两次 |

**含义**

- 合并语义**只需定义一次**（"按记录种类逐类合并"），部分导出只是"包里装得少"。
- 包是**自描述**的 → 天然承载 F3 修复所需的"本包未携带本地图标"声明。
- 判据 B（可解释）的清单与判据 A（保真）的 diff，**可共用同一次解析结果**。（原第 3 项"判据 C 的快照"随 G4-C 撤回而失效。）

---

### G3 — 包内可承载的记录种类

**决策**：**B — sync 层 + 可选「图标数据」附件（opt-in，默认关）。**

> **⚠️ 已被取代（2026-10-04）**：本决策由 Constraint 层 **C1** 取代 —— 用户裁定「图标只支持导出 Icon URL / local-icon 路径 / Custom Icon 配方」，故**包内禁止任何原始位图**，opt-in 开关与体积上限**均不再需要**。本条的三个衍生结论（包内声明、体积上限、`MAX_OUTPUT_SIZE` 欠账）**全部作废**。详见 `2026-10-04-import-export-constraint-boundaries-design.md` §0.2。

- 始终入包：`slots`（含 `uiMarker` 的 URL / 模板图标）、`rules`、`matchSettings`、`switchDirection`、`autoBindGlobal`。
- 可选附件：上传类图标的 data URI。导出时可勾选；包内**显式声明**"含本地图标数据"。
- 默认不带时：接收方看到占位 + **明确的"需重新选择"提示**。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 仅 sync 层 | 使"分享单条规则/槽位"名不副实 —— 对方拿到占位图标且不知要重选，正是 G1 要消灭的静默降级 |
| C. sync + 本地层附件（`tabOverrides`/`siteSnapshot`/`iconCache`） | 抵触设计权威 `constraints-permissions-privacy-design.md:41`；`bindings`/`siteSnapshot` 是设备与会话语义，跨机导入会产生指向不存在 tabId 的记录（引入新的静默错误） |

**含义**

- 容量边界原样保留（默认关闭），隐私边界不变。
- ⚠️ 遗留待约束：**图标体积上限**需在 🔒 Constraint 层决策（data URI 可达 64 KB/个，10 槽位即 640 KB）。

### G4 — 成功判据

**决策**：**D — 三条全部为硬指标**，工期冲突时按 **B > A > C** 取舍。

> **⚠️ 部分撤回（2026-10-05）**：**G4-C（可逆）已撤回** —— 用户裁定「不需要实现导入撤销」。G4 现只剩「保真」与「可解释」两条硬指标，取舍顺序为 **`B > A`**。详见 `2026-10-04-import-export-constraint-boundaries-design.md` §0.3。

| 判据 | 定义 | 所堵缺陷 |
|---|---|---|
| **A. 保真** | 全量包 导出→导入 等价无损；任一导入路径不得改动用户未勾选的记录，须有测试证明 | F2（静默替换） |
| **B. 可解释** | 导入前展示**每条记录将发生什么**（新增/替换/保留/跳过 + 原因），且与提交结果**逐条一致**（预览是合同，不是估计） | F3 + 只有两个单选按钮 |
| ~~**C. 可逆**~~ | ~~任一导入都是**单次可撤销操作**，与既有 5 秒 UndoBar 同一语言；撤销后状态与导入前逐字段等价~~ | **已撤回（2026-10-05）** |

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 单一判据（A / B / C 之一） | 三条互不替代，各自堵一类真实缺陷 |

**含义 / 张力**

- C 要求保存"导入前状态"，而导入会改 `slots` + `rules` + 3 个全局字段 —— 规模远大于既有单槽位覆盖快照，**撤销的承载形态是架构层首个决策**。
- "无兼容包袱 + 单一 schema"使三条同时达成的成本很低：包自描述 → 同一份解析结果派生 diff / 清单 / 快照。

---

### G5 — 导入边界

**决策**：**B — 文件驱动 + 明确的「清空」指令。**

- 文件里有什么就只动什么；未出现在文件中的记录**永不触碰**（含规则：无 `rules` 键则完全不碰规则）。
- 允许包声明"本包代表完整状态，导入即覆盖"（等价旧 `replace`），但**必须由用户在预览中显式勾选**，不得靠推断。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 一律文件驱动 | 无法表达"恢复成某个已知状态"（灾备/迁移的真实诉求），退化为"先手动清空再导入"两步 |
| C. 一律全量覆盖 | 正是 `state.rules = preview.rules` 的现行行为，即 F2 的根源 |

**含义**

- 两种意图都保留，但**强制显式表达** → 天然满足判据 B。
- diff 与快照规模可被用户预期。

## 3. 本层结论摘要

| 编号 | 项 | 决策 |
|---|---|---|
| G1 | 迭代目标 | B + C 并做，不背兼容 |
| G2 | 传送模型 | 版本化可携带包，全量与子集同构 |
| ~~G3~~ | ~~记录种类~~ | **已被 C1 取代（2026-10-04）** —— 包内禁原始位图，只带 URL / 裸引用 / 可复现配方 |
| G4 | 成功判据 | 保真 + 可解释（~~可逆~~ **已撤回**；`B > A`） |
| G5 | 导入边界 | 文件驱动 + 显式"清空"指令（**已精细化**为按维度模式，见架构层 §0.1） |

**使命一句话（2026-10-05 修订）**：把导入/导出从"两个单选按钮 + 静默整体替换"改造成**一个自描述可携带包**，其导入过程**可解释、可保真**、且由**按维度显式选择的模式**决定边界，并让"分享单条规则/槽位"与"全量迁移"走同一套语义。
