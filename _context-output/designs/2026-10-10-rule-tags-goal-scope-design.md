| # | 发现 | 证据 | 影响 |

## 2. 决策记录

### G1 — 标签的语义层级

**决策**：**A — 纯组织标签。**

创建/编辑规则时可打多个标签，Rules 页可按标签筛选。标签**不影响**规则的匹配、优先级、启用状态。**规则执行行为与今天完全一致。**

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| B. 组织标签 + 批量操作入口 | 数据模型成本为零（`string[]` + 循环写入），**推迟代价极低**；先做则须同期设计目标语义（覆盖/新增/移除）、误操作确认与撤销，是独立工作量 |
| C. 标签即分组实体 | 为一个「找到规则」的需求引入可改色/可排序/有引用完整性的子系统：重命名传播、删除语义、孤儿引用。YAGNI |
| D. 标签参与行为 | 会让「改标签」与「切换行为变化」耦合，产生不可解释缺陷；与 B2 的证据直接冲突 |

**含义**

- 标签是**惰性数据**：只被 UI 读取，不进入 `resolveFieldChain` / `selectWinningRule` / 投递路径。
- 「管理更多规则」的痛点被定位为**找到**规则，而非规则的行为。

> **⚠️ 范围修订（2026-10-11，🔒 Constraint 层回溯）**
>
> 用户在约束层选择了 **B（全局标签表 + 规则存 id）**，并追加两项要求，故本决策的**「惰性数据」表述被取代**，但**语义决策（不影响匹配/优先级/启用）依然成立**：
>
> 1. **需要一个独立的标签管理界面**（增删改查）——标签由「字段值」升格为**一等实体**，拥有自己的生命周期（重命名、删除），而非仅是规则上的一个字符串。
> 2. **后续迭代有其他系统也会用到 tag** —— 标签是**跨系统**的组织维度，因此实体必须定义在**共享层**、而非嵌套在规则之下。
>
> 不变的部分：标签仍**不进入**执行链。升格的是**它的存储与生命周期**，不是它对规则行为的影响。
> 影响：G3 的入口范围需追加「管理界面」（见 G3 修订）；本迭代的复杂度主要来源从「表达式引擎」变为「表达式引擎 + 实体生命周期（重命名传播 / 删除的引用完整性）」。

### G2 — 规模假设（界面按此设计，不写死上限）

**决策**：**B — 50–300 条规则、几十个标签。**

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. ≤ 50 条 | 与「管理更多的规则」的自述不符，会导致筛选控件过于简陋 |
| C. 300+ 条 | 虚拟化与标签命名空间只有在真到量级时才付得起；**推迟成本为零**（`tags: string[]` 在 A/B/C 下同形，长大无需迁移数据） |
| D. 不确定 | 与 B 的实际产出相同，但缺少用于设计 UI 的明确目标 |

**含义**

- 需考虑标签的**呈现方式**（候选面板 vs 纯下拉）与**每个标签的规则计数**。
- **不引入**：列表虚拟化、层级标签（`work/`）。
- 规则数量与标签数量是**两个独立**的规模问题（见 G3）。

---

### G3 — 标签的赋予入口

**决策**：**B — 新建时 + 单条编辑时。**

新建可打标；编辑已有规则时可改标签（含清空）。

> **⚠️ 范围修订（2026-10-11，🔒 Constraint 层回溯）**：追加第三处入口——**独立的标签管理界面**（标签自身的增删改查）。它管理的不是「把标签贴到规则上」，而是**标签实体本身**的生命周期；「给规则贴标签」仍只发生在本决策已定的两处。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 仅新建时 | **致命**：存量规则永远没有标签 → 按标签筛选对它们恒为空，特性「看起来做完了但用不了」 |
| C. 加上批量赋值 | 见 G1-B：推迟代价极低，且抓手已存在（B5） |
| D. B + 从当前筛选结果反推批量 | 同上；且「先缩小范围、再一次性命名」的路径可由 C 顺带覆盖 |

**含义**

- 让标签筛选**不落空**的最低限度是 B。
- 批量赋值被登记为**明确的下一步**，其入口位置已可预见（Rules 页现有的批量操作栏）。

### G4 — 多条件的筛选语义

**决策**：**D' — 用户可编辑布尔表达式（AND / OR / NOT / 括号优先级）。**

> 选项 D 原为「AND/OR 可切换」；用户在 D 的基础上**扩大为完整布尔表达式**，本决策按扩大后的语义记录。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 单选一个标签 | 无法表达「工作或紧急」「除了归档之外的」这类真实意图 |
| B. 多选 AND | 选中 3 个标签常得**空列表**，用户会误判为「标签没打上」——空结果是最易让人对特性失去信任的失败模式 |
| C. 多选 OR | 只能放宽不能收窄，无法表达 `work AND urgent` |

**含义**

- 筛选条件是一个**布尔表达式**，而非一组勾选。其求值需要一个自研表达式引擎（见 G5）。
- **本层只定语义，未定求值落点**（UI 内 / 共享模块）——该问题在 🏗️ Architecture 层回答。
- 引入一个新的组成部分：**表达式引擎**（AST + 求值 + 合法性判定）。这是本迭代**最主要的复杂度来源**。

---

### G5 — 表达式的输入形态

**决策**：**结构化构建器（chip 序列）+ 自研解析器；无自由文本表达式。**

- 搜索框为 **chip 输入框**：点选标签、点选 `AND` / `OR` / `NOT` / `(` / `)`；
- 点选后每一项进入框内、**左对齐**、成为**可单独删除的小标签**；
- 框内的文本输入**只用于筛选候选标签列表**，不用于书写表达式本身。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 纯文本输入 + 解析器 | 用户需自行书写语法并记住运算符与括号；拼写错误、非法字符成为一整类需要提示的错误状态 |
| C. 文本 + 宿主求值器（`new Function` 等） | 把表达式语义交给宿主语言，校验一旦有缺口即为任意代码执行；B7 亦无库可用 |
| D. 文本 + 结构化混用（双向） | 最贵的是 **AST→文本** 方向（加括号不得改变语义），而「可点选」的收益已被 chip 构建器以更低成本取得 |

**含义**

- **分词器（tokenizer）不再是必需项**：chip 序列**本身就是 token 流**，用户无法输入任意字符，因此不存在「非法字符」「拼错的运算符」这类错误。
- **解析器仍然必需**：负责优先级、括号配对、元数（arity）校验；但它消费的是已经结构化的 token，而非字符流。
- 该形态解锁一项待决优化（登记于 🏗️ 层，不在本层决定）：**因为下一步候选有限，可以只提供「能保持表达式合法」的选项**，使「构建出语法错误」在 UI 上近乎不可达，而不是事后报错。
- 「优先级（括号包裹）」被保留为**一级表达能力**，与 G4 的布尔表达式语义一致。

---

### G6 — 表达式的变量范围

**决策**：**A — 只有标签。**

谓词形如 `work`、`NOT archived`。候选列表**始终完整**（标签是有限集），UI 不可能给出「不存在的变量」。标题 / URL 的查找**继续由现有的文字搜索框承担**（`filteredRules`，见 B6）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| B. 标签 + 标题/URL 条件 | chip 内出现自由文本 → 引号转义规则、匹配模式（包含/通配/正则）、以及「表达式合法但匹配式无效」的**第三类错误状态**。把「分类筛选」问题升级为「通用查询语言」问题 |
| C. 只有标签但预留 `field op value` 形状 | 与 A 实现成本几乎相同；未采纳的理由：当前**无第二个字段**，预留形状会在数据模型与测试中常驻一个空维度。若后续确有需要，届时迁移成本仍低（表达式是 UI 态，见 🏗️ 层） |

**含义**

- 「不存在的标签」这一类错误**在结构上不可能出现**：候选来自实际标签集。
- 两个控件**语义互不干扰**：chip 表达式 = 分类筛选；文字搜索框 = 字面查找。
- 现有文字搜索行为**零回归**。
