## 0.3 本层修订（2026-10-05）：撤回「导入撤销」

用户裁定：**不需要实现导入撤销的功能。**

**受影响的决策**

| 编号 | 原决策 | 现状态 |

**后果（显式记录）**

- `覆盖导入` 成为**不可逆的数据销毁操作** —— 此前其唯一的恢复手段即撤销，现已移除。
- C3 的原子性只防「**失败**」，不防「**成功地做错**」。
- C11-C（覆盖未携带维度需独立确认）依然有效，但其覆盖面**不足以**覆盖「整个覆盖导入」的破坏性。

**替代保障（待架构层裁定）**：破坏性导入前是否需要「先导出备份」的显式二选一。

## 1. 决策记录

### C1 — 包内图标承载红线

**决策**：**包内禁止原始位图**。只承载三类图标：

| 类型 | 承载形态 | 导入方行为 |
|---|---|---|
| `Icon URL` | 纯字符串（`http(s):`） | 直接可用；缓存由接收方自行建立 |
| 上传类 | `local-icon:` **引用** | 解析必然失败 → 缺失占位 + 清单告知 |
| Custom Icon | **可复现配方**（背景色 / 文本或 Emoji / 文本色） | 渲染时还原（分辨率无关，比位图更清晰且更小） |

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 始终附带 data URI | 单图标可达 ~2.7 MB（2 MB 输入 × base64 膨胀），10 槽位即 ~27 MB，文件无法传递 |
| 默认不附带、可 opt-in | 仍需承载位图与包内声明；而 URL 缓存图标交由接收方「首次需要时建立本地缓存」，更贴合既有边界 |

**含义**

- 体积天然受控 → 无需上限、无需 opt-in 开关。
- **免除了 `MAX_OUTPUT_SIZE` 的欠账**（该常量从未被引用；`icon-service.ts:341` 明写 "For now, store the data URI directly"）。
- **附带范围扩张**：新增「Custom Icon 配方持久化」。今日 `Custom Icon` 的 `bgColor`/`text`/`textColor` **随写随丢**（`sidebar/App.tsx:933`、`rule-form-submit.ts:80`、`settings/App.tsx:1657` 均先 `renderIconToDataUri` 再写 `{type:'upload'}`），`IconSource.type:'template'` 在全仓**从未被产出过**。

**已核实的事实（对裁定的支持）**

- 配方渲染走 `renderIconToDataUri` → canvas 默认 `image/png`，属 `isSafeFaviconProtocol` 允许的 bitmap 子类型 → **与既有 favicon 安全闸门天然相容**。
- `IconConfig`（`IconEditor.tsx:17`）已是 `{ bgColor?, text?, textColor?, dataUri? }` → **导出/导入时有接口可用，无需新造**。
- ⚠️ 但 `IconSource`（`types.ts:57`）**没有 textColor 字段**，且从未用它承载配方 → 配方持久化需要 schema 工作。

### C2 — 导出前必须解引用，且裸发引用

**决策**：导出**不得**写 `[local:…]` 包装；上传类图标一律裸发 `local-icon:…`。

**依据（现网缺陷）**

```49:49:src/background/import-export-service.ts
              ? { ...slot.uiMarker.icon, value: slot.uiMarker.icon.type === 'url' ? slot.uiMarker.icon.value : `[local:${slot.uiMarker.icon.value}]` }
```

- `import-export-service.ts:49` 产出的是 **`[local:local-icon:icon:slot-3]`**；
- 解析逻辑判断 `startsWith('local-icon:')`（`storage-repository.ts:416`）—— 带包装后**首尾都不匹配**；
- 于是它**永远解析不了**，也**不被识别为引用**，导入后只以字面量存在（UI 破图 / favicon 侧被安全闸门静默丢弃）。

**同时**：`getSyncState()` 每次读取都会 `resolveIconReferences` 把引用还原为真实 data URI（`storage-repository.ts`），所以导出拿到的是**已解引用的 data URI** → 必须**重新识别并转回引用**，而不是原样导出。

**含义**：URL 类直接导出 URL（本就可复现），不上引用。

### C3 — 导入严格原子（F4 并入本层）

**决策**：**严格原子**。预检全部通过才允许提交；提交是**单次配置写入**（沿用既有单一写入服务）；任一硬约束不满足（配额不足 / 版本冲突 / 记录非法）→ **整体拒绝、配置零改动**，并明确告知**哪一条**挡住、**怎么化解**（如"减少勾选范围"）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 尽力而为（部分成功） | 使判据 B（预览即合同）与 C（撤销 = 回到导入前）同时失效，产生"勾了 12 条只进去 7 条"的不可解释状态 |
| 原子 + 配额降级通道 | 把同一决策拆成两次勾选，违反 G5「意图显式表达一次」；配额不足的正确回应是回到勾选环节 |

**F4 正式并入**：今日 UI 发 `IMPORT_COMMIT` **不带** `configVersion`（`settings/App.tsx:2073`），后端 `?? this.repo.getConfigVersion()`（`worker-orchestrator.ts:756`）取**当前**版本 → `writeSync` 乐观锁**必然通过**，预览到提交之间的漂移不被 `STALE_VERSION` 拦截。

→ 原子提交必须在**预览时确定的版本号**上执行，否则"零改动"无法保证。

### C4 — 提交权威在服务端

**决策**：**服务端重新推导**。UI 只回传**用户意图**（选中了哪些记录 / 是否声明"清空"）；服务端**重新解析文件并重算 diff**，与预览比对，不一致则拒绝并回到预览。**preview 仅用于展示。**

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 服务端缓存预览（token） | **MV3 下不可靠** —— service worker 随时可能被挂起，预览与提交之间的内存状态会丢失（正因如此既有 `pendingUndo` 采用 lazy `expiresAt` 校验） |
| 维持现状（UI 回传完整 preview）+ 加强校验 | 权威在客户端，使判据 B 退化为礼貌性提示；且 UI 原样回传 `preview` 等于允许**绕过 G5「清空需显式勾选」** |

**依据（既有注释自证）**

```176:179:src/background/import-export-service.ts
    // T31 (B4-3): re-run the regex safety gate HERE rather than trusting
    // `preview.valid`. The preview is caller-supplied and may have been built by
    // hand or mutated between PREVIEW and COMMIT, so the earlier check is only a
    // UX guard — this is the enforcement point (closes the TOCTOU window).
```

> **📐 层补充（2026-10-05，A15）**：C4 的「包必须自描述」前提**依然成立**，但**文件漂移**这一残余风险被**构造性消除**：UI 复用 `INSPECT` 读到的那一份字符串传给 `APPLY`，预览内容与写入内容在构造上同一，故无需比对文件、无需指纹、无需重读。**权威性 + 告知性同时得到保证**（先前 A5 只保证了权威性）。

**前提（架构层须兑现）**：**包必须自描述** —— 服务端要能仅凭「文件 + 意图」重算，不能依赖客户端补充包内语义。这也顺带消灭一个**未被识别**的缺陷：今日"文件驱动 vs 清空"这个意图**在传输中根本不携带**。

### C5 — 撤销快照的存储红线

**决策**：**只存 `storage.local`**，**独立键 + TTL 惰性失效**（复用既有 `pendingUndo` 的 lazy `expiresAt` 模式），**不设预设大小上限**，信任 local 配额。

**技术上不可协商的前提**：快照**绝不能写入 `storage.sync`** —— sync 是跨设备共享配置（写入会让 A 设备的快照出现在 B 设备），且 sync 单键 8 KB 装不下。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 明确的容量上限 + 上限不满足则拒绝 | 用户选择"不预判体积"，信任配额 |
| 允许存 sync（支持跨设备撤销） | 违反 sync 语义边界与 8 KB/键限制 |

### C6 — 快照写入失败的处置

**决策**：**仍然执行导入，但显式告知"本次不提供撤销"，由用户自行确认。**

**与 G4 的关系（显式记录，避免日后被当作矛盾）**

G4 声明"可逆"为硬指标；本条打开了"经用户确认可放弃撤销"的通道。二者**不冲突** —— **G4 自身的取舍顺序支持它**：`B > A > C` 中可逆优先级**最低**，因此"用户明确知情后放弃撤销"与既定顺序一致；而"拒绝执行"实际上是把可逆抬到**高于用户意图**，反而与 G4 顺序不符。

**硬前提**：放弃撤销必须是**一次独立的确认**，不得混在普通提交里 —— 否则判据 B（预览即合同）被"先斩后奏"破坏。

**派生架构要求（记入 🏗️）**：须在**提交前**告知"本次不提供撤销" → 预览阶段必须**探测快照可行性**（快照内容在预览时已知、体积可算、可用配额可查）。提交路径因此有**两种终止态**：

```
快照成功 → 可撤销
快照失败 → 二次确认 → 可放弃撤销
```

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 拒绝执行导入 | 把可逆抬到高于用户意图，与 G4 顺序不符 |
| 先腾空间再重试（清 iconCache） | 会**静默删除用户的图标缓存** —— 新的破坏性副作用，把一个失败路径扩成两个决策 |

---

### C7 — 失败路径无需撤销

**决策**：**导入失败不需要实现撤销功能。**

**性质**：这是**澄清**而非改变 —— 由 C3 自动推出：

```
严格原子 ⇒ 失败 = 零改动 ⇒ 没有任何东西需要撤销
```

- 撤销只服务"**成功**但想反悔"；
- **不改变 C10-③**：③ 服务的是成功路径（恢复被清空的图标键），无需为失败场景设计快照；
- **不改变 C6**：C6 处理的是"**成功**导入但快照写入失败"，与"导入本身失败"是两件事。

### C8 — 包校验：宽容读取 + 逐项披露

**决策**（用户原话，记为选项 D）：**宽容读取 + 逐项披露 + 用户确认** —— 未知字段忽略、缺失可选字段取默认值，**但每一处宽容都是一条可见的预览条目**，用户确认后才执行；仅结构性错误（非对象 / 缺关键数组）直接拒绝。

**核心语义**：宽容 **≠** 静默。把"我替你做了决定"变成"我告诉你我打算怎么处理，你同意再说"。

**三条边界（用户已确认）**

1. **宽容适用范围**：**仅限同 schema 版本内的未知字段与缺失可选字段**。**版本不符仍严格拒绝**（G1 已定"不背兼容"）—— 否则宽容会变成"跨版本尽力导入"。
2. **宽容不降低原子性**：宽容只发生在**预检阶段**，C3 不变 —— 能宽容的进入预览，不能宽容的整体拒绝、配置零改动。
3. **派生要求（📐）**：判据 B 的行项从 4 类扩为 **6 类**，增加 `忽略未知字段` 与 `填充默认值`；证据粒度需在 📐 层定（若一个文件有 50 处未知字段，逐条确认会淹没预览，届时可能汇总为"本包含 N 处将被忽略的字段（展开可见）"）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 全严格（任一即拒绝） | 用户选择保留可读性，但要求每处宽容可见 |
| 宽松读取（静默取默认） | 把"文件损坏"变成"静默改配"，正是 F3 类缺陷的根源 |

### C9 — 未携带图标的落库形态

**决策**（用户原话，记为选项 D）：**保留引用字符串（裸引用）+ 一次性告知** —— 上传类图标落库为**本地路径引用**（既有语义）；导入方该引用指向的本地键不存在时即为不可解析，"需重新选择"**只在导入结果清单里告知一次**，不持久化额外标记。

**两条边界（用户已确认）**

**① 导出必须发出「裸引用」，不能加包装** —— 见 C2（这是无论选哪个方案都必须修的现网缺陷）。

**② "缺失"必须由消费方判定，不能靠字符串自证** —— 引用解析失败时 `resolveIconReferences` 会把值**原样留下**（`if (actualUri)` 才替换），字面量会流到 UI 与 favicon 路径。因此需要一条消费方规则：

> **引用无法解析 ⇒ 视为"缺失图标" ⇒ 显示占位**（而非当成字面值渲染）

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 值置空（unset） | 只能满足"告知"，无法满足设计要求的「展示占位」（`constraints-…-privacy-design.md:41` 是**持续状态**而非一次性通知） |
| 值置空 + 持久化"待重选"标记 | 需扩展 `IconSource`；而 D + ② 已能由解析结果推导出同一状态，**无需动 schema** |
| ⚠️ 保留占位字符串（今日 `[local:…]`） | **已证否**：见 C2，带包装的字符串永远解析不了也不被识别为引用 |

### C10 — 替换记录须清空其图标存储槽

**决策**（用户原话，记为选项 D）：导入写某个 slot/rule 时，**先清掉目标机上该记录遗留的本地图标键**（`icon:slot-3`），再写入导入记录。于是"未携带的图标引用"在目标机上**必然解析失败** → 稳定落入"缺失" → 占位 + 清单告知一次。

**所堵缺口（本层交叉审查发现）**

引用键由**记录 id 派生**（`storage-repository.ts:387/400`：`icon:${rule.id}` / `icon:slot-${slot.id}`），slot id 恒为 `1..10`。解析仅判断 `startsWith('local-icon:')` 后取同名键（`:460-464`）。于是：

| 目标机状态 | 结果 |
|---|---|
| 无该键 | 解析失败 → 缺失占位 ✅（预期路径） |
| **恰好也有 slot 3 且其图标也曾转存** | **键存在 → 解析"成功" → 取到目标机自己的图标 → 静默显示成另一张图标** ❌ |

**"假成功"比破图更糟**：用户看到一张正常图标，不会去重选，也不知道值已被悄悄替换。

**补充事实**：今日 `[local:…]` 包装**碰巧**躲开了这个碰撞（带包装的字符串永不匹配前缀，故永远解析失败）—— 即 C2 修好导出后，**这个隐患才被暴露**。所以它不是"要不要修"，而是"怎么修"。

**为何优于"引用键加内容哈希"**

原有推荐（转存键加入 hash/uuid）会迫使**迁移**：现存所有 >6 KB 图标**已**以 `icon:slot-N` 落库，而那是它们的**唯一副本** → 改键格式会让用户眼下的图标**集体变缺失**，属**数据回归**而非格式不兼容。本方案保留键格式、无需迁移，并有**顺带收益**：被替换记录遗留的图标数据本就是孤儿，清掉即**避免本地存储泄漏**。

**更准确的框架**：清空不是附加动作，而是"**替换记录**"的自然组成 —— 记录的图标存储槽**属于该记录**，替换记录即替换它的存储槽。

**三条派生要求（用户已确认）**

| # | 要求 |
|---|---|
| ① | **作用域严格**：只对**本次真正写入**的记录执行（`decision='import'`）；`keep existing` 的记录**一个字节都不动**（G4-A 保真） |
| ② | **与写入同属一次原子操作**：清空发生在**同一次写入内**，失败即整体回滚 —— 否则"先清后写"若写入失败，就白白删掉目标机的图标数据（违反 C3） |
| ~~③~~ | ~~撤销快照必须覆盖被清空的图标键~~ —— **作废（2026-10-05）**：不实现撤销，清空即为**永久删除** |

**③ 作废的后果（2026-10-05）**：被替换记录的图标数据**直接删除、不可恢复**。由于 `覆盖导入` 本身也已不可逆（见 §0.3），**误选覆盖 = 图标与配置同时永久丢失**。原 🏗️ 候选（"改名而非删除"）随 ③ 一并失效。

## 2. 本层结论摘要

| 编号 | 项 | 决策 |
|---|---|---|
| C1 | 包内图标承载 | 禁原始位图；只承载 URL / 裸引用 / 可复现配方 |
| C2 | 导出解引用 | 必须解引用并**裸发**（去掉 `[local:…]` 包装） |
| C3 | 导入原子性 | 严格原子 + F4（绑定预览版本号）并入 |
| C4 | 提交权威 | 服务端重新推导；preview 仅展示；包须自描述 |
| ~~C5~~ | ~~快照存储~~ | **作废（2026-10-05）** —— 不实现导入撤销 |
| ~~C6~~ | ~~快照失败处置~~ | **作废（2026-10-05）** |
| ~~C7~~ | ~~失败路径无需撤销~~ | **作废（2026-10-05）** —— 澄清对象已不存在 |
| C8 | 包校验 | 宽容读取 + 逐项披露 + 确认（仅同版本内；版本不符拒绝） |
| C9 | 未携带图标 | 裸引用 + 消费方判定缺失 + 清单告知一次 |
| C10 | 替换记录 | 同步清空其图标存储槽（作用域严格 / 原子 / 快照覆盖） |

**一句话（2026-10-05 修订）**：包内**不搬运字节**（只带 URL、裸引用、可复现配方）；导入**要么全成要么零改动**、由**服务端**依**文件 + 显式意图**重新推导、失败与版本不符一律拒绝；**不提供撤销** —— 因此 `覆盖导入` 是不可逆的销毁操作，其唯一保障是原子性与显式确认。
