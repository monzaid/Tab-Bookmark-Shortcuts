## 1. 决策记录

### A1 — 标签写入路径的归属

**决策**：**B — 独立 `TagService` + 独立消息族。**

`CREATE_TAG` / `RENAME_TAG` / `DELETE_TAG` / `SET_RULE_TAGS`；标签表由 `TagService` 独占；**`RuleService` 只负责规则内容，不感知标签表的存在**。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 扩展 `RuleService` 与现有消息 | 改标签会顺带经过 `applyToMatchingTabs`（该路径写死在 rule-service 内，见 F2）。结果虽幂等，但把「标签不影响行为」这条不变量**从结构约束降级为巧合**，违反 G1 |
| C. `StorageRepository` 直接暴露方法 | 把业务规则（上限校验、trim 去重、级联语义）下沉到存储层；`StorageRepository` 现有方法几乎都是纯搬运，会破坏其分工 |
| D. B + 谓词求值也归 `TagService` | 按表达式筛规则是**纯函数**，宿主（UI）已持有全部规则；放进背景层会把同步计算变成消息往返，是明确性能倒退。O1 由此排除「背景层」 |

**含义**

- **重投递隔离由模块边界保证**，而非靠调用者自觉：`TagService` 根本没有投递入口。
- **「其他系统也会用到 tag」**（G1 修订）依赖的正是这条边界：未来系统依赖 `TagService`，而非依赖「规则服务里顺便管标签」。
- `PageRule.tagIds` 对 `RuleService` 是**透明数据**——它读得到但要理解不了，删规则时也不会去清理标签侧。故 **D3（剥离悬空 id）的落点必须在 `TagService` 的写入路径**，不能指望 rule-service。

### A2 — 表达式引擎的落点

**决策**：**C — `src/shared/` 纯模块，并把「实体解析」一并下沉。**

新建 `src/shared/tag-expression.ts`：无 React 依赖、无 chrome 依赖；**AST 类型成为共享契约**；`ui` 只负责「AST ↔ chip 序列」的呈现与点选。

其中「实体解析」指：**「表达式 + 标签表 ⇒ 规则子集」的求值**（即依赖 `tags: {id,name}[]` 做**名字 ↔ id** 解析的那部分），而不只是纯语法层。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. `src/ui/shared/` | 与 chip 构建器同级 ⇒ AST 类型不对外暴露，「其他系统复用」会退化为**重写一遍解析** |
| B. 仅纯语法层下沉 | 边界画错位置：chip 存**名字**（用户可见可点选），规则存 **id**（C1），故求值**必然**需要标签表做名字↔id 解析；留在 UI 等于让 UI 单独承担 C1 决策的后果 |
| D. 实现在一处、类型在另一处 | 类型与实现是同一契约的两半，分开只会「改一处忘另一处」 |

**含义**

- 「**标签名 → 规则子集**」成为共享层的一个**纯函数**——这正是未来系统要复用的东西。
- 解析与求值落在 `vitest --project unit`，可用**纯函数穷举单测**；**D1（不得因深度崩溃）** 在此获得最佳覆盖手段。
- 本迭代的**语义中枢**：无宿主依赖 + 纯函数 + D1 三条约束同时落在这一处。

### A3 — 包内标签的承载形态

**决策**：**根级 `tags: string[]` + `PortableRule.tags: string[]`（内联名字）。**

> 用户在 A/B/C/D 之外给出了**组合答案**：根级表 + 规则内联名，与 C（仅名字）一致，并额外要求**导出侧的界面维度与不自洽弹窗**（见 A5）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 与 `SyncState` 1:1 镜像（规则带 id、根表带 id） | 包内**规则用名、表用 id** 两套身份并用（见 A4），自洽校验退化为两件事；且会让人误以为包内 id 有意义 |
| C. 规则内联名、包内不设标签表 | 无「词汇表」承载对象 ⇒「哪些标签作为实体被携带」不可表达，与 A5 的维度选择冲突 |
| D. 宽容导入（静默丢弃悬空 id） | 会让导入**部分成功**：用户看到某条规则少了标签却无任何提示。与 `import-export` 迭代全力消灭「静默降级」的立场相反 |

**含义**

- **`PortableRule.tags` 落地受 F3 强制**：`RULE_KEYS` 必须新增 `tags`，否则**编译失败**（护栏已存在，不需新增机制）。
- 根级 `tags` 不受 `RULE_KEYS` 管（它是新位置），但**新增第 5 个导出维度**需同步 `ExportScope` / `DimensionPresence` / `DimensionMode`（F6），与既有 4 维度的机制保持一致。
- **包内自洽的判定 = 一行集合差集**：`union(被导出规则的 tags) \ 根级 tags` 非空 ⇒ 不自洽。该差集**同时**是 A5 弹窗要报的内容、以及「补足」与「丢弃」两个选项共同的操作对象。
- **路径选择记录**（本层内部比较，非用户裁决）：本层曾把「包内标签表按被携带规则裁剪」列为建议（选项 B），用户实际给出的方案**在导出侧就消灭了不自洽**，从而让落盘文件**永远自洽**、导入侧保持 C9 的严格姿态。**问题在用户有上下文的地方（导出）解决，而非在他没有上下文的地方（导入）解决**——此路径**优于**原建议，记录为已采纳。

### A4 — 包内 `tags` 表的条目形态

**决策**：**C' — 根级表携带标签实体，规则内联名字。**

根级 `tags: PortableTag[]`（`{ name, backgroundColor, textColor }`——**不携带 id**）；`PortableRule.tags: string[]`（内联名字，仅名字，因为规则只引用名字）。

标签表在包内是一个**词汇表**；自洽 = 每条规则的每个名字都出现在该数组中。

> **⚠️ 回溯修订（2026-10-11，📐 Detail 层收尾）**
>
> 原决策是 `string[]`（**仅名字**），前提是「标签只有名字」（C1 原稿）。C1 扩展出 `backgroundColor` / `textColor` 后，仅名字的词汇表**传不了颜色**，故根级表改为携带实体属性。
>
> **仍然不携带 id**（原决策的真正理由不变）：目标机已有自己的一套标签 id，包内 id 无承载对象；导入时按**名字**重算 id（命中复用、未命中新建）。**规则侧照旧只内联名字**——规则引用的是名字，而 C2 规定名称即身份。
>
> **形状**：`PortableTag` 与 `PortableIcon` 的 recipe 分支**同形**（`bgColor`/`textColor` 的命名差异在实现期统一，见 📐 层术语表）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. `{id,name}[]`，按名字查找/新建，源 id 仅用于包内自洽校验 | 镜像收益是假的：id 在本机存在**只因为规则存 id**（C1）；包内规则存名，动机消失。且会诱使后续实现依赖一个无语义的 id |
| B. `{id,name}[]` 保留源 id | 需 id 空间冲突与重映射策略，而两套 id 之间**无任何语义关联**（同名即同一标签），纯自找复杂度 |

**含义**

- **用户补充的关键论据**（本决策的决定性理由）：*目标机已经有自己的一套标签 id，包内记录的标签 id 无用，导入时必须重算 id。*
- **导入侧数据流因此确定**：`名字 → 本地 id`，按 C2 的 **trim 后逐字节相等**匹配；**命中则复用、未命中则新建**。包内 id 从不存在 ⇒ **无 id 空间协商**。
- 代价（可接受）：`PortableRule.tags` 与根级 tags **都按名字**，故「重命名」在包内表现为名字变化——对**一次性传包**无影响（不像本机需要 id 稳定）。

### A5 — `tags` 维度的自定义粒度与不自洽弹窗

**决策**：**B — 支持逐标签勾选**（与 rules 的逐条勾选对称）。

排除一个正在被使用的标签 ⇒ 该标签成为**悬空名** ⇒ **导出前弹窗**生效，提示不自洽并提供两个选项：

1. **补充 tags 到自洽最小集**（即把差集里的名字补进根级 tags 表）；
2. **丢弃每个规则里的悬空 tags**（即从被导出规则的 `tags` 中移除差集里的名字）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 维度级开关（全带/全不带） | 会使本决策要求的弹窗成为**永不触发的死代码**：它保证包恒自洽 ⇒「不自洽」状态在结构上不存在 ⇒ 两个补救选项都无触发场景 |
| C. 逐标签勾选但禁用正在被使用的标签 | **把选择权收走**：用户可能有合理意图「只分享规则结构、不带我的标签分类」，C 下无法表达 |
| D. B + 勾选阶段实时显示影响 | 有价值但是**可选**增强：用户明确要的是**导出时弹窗**；D 不需改协议，仅改面板渲染，可后续追加 |

**含义**

- **弹窗的两个选项与集合差集一一对应**，无第三态：`补充` = 把差集并回根级 tags；`丢弃` = 从规则内联名中减去差集。二者都**不产生悬空**。
- **两条出路都是纯数据操作**，不涉及本机标签实体的增删 ⇒ 不会与 C4 的级联语义纠缠。
- 导入侧不受影响：**落盘文件恒自洽**（A3 含义），故导入侧继续按 C9 的**严格姿态**处理（缺失即损坏）。
- **维度语义待 📐 层明确**：`tags` 单独导出（不带规则）时，目标机应**创建该词汇表**（只增实体、不碰引用）；该场景无害且与 A3 的自洽判定不冲突。

### A6 — `tagIds` 的存储方向

**决策**：**A — 规则存 id（`PageRule.tagIds`）+ 标签表只有 `{id, name}`。**

反向问「哪些规则用了标签 X」需**遍历规则**——用于 C4 的删除确认与 C3 的孤立标签识别。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| B. 标签表存 `ruleIds`，规则上无字段 | ① **方向反了**：规则行渲染（每条规则都要显示标签）是**最高频**读取，B 让它变成遍历；反向问是低频的，遍历更划算。② **破坏 A1 的模块边界**：规则删除走 `RuleService`，而它按 A1 **不感知标签表**——B 下删规则必须回头清理标签表上的 `ruleIds`，tag 知识重新渗进 rule-service |
| C. 双向都存 | 一致性的维护要覆盖 创建 / 更新 / 删除 / 导入**四条路径**，任一条漏更新即静默不一致 |
| D. A + 惰性反向索引（不落盘） | 解决的是「反查变慢」，而标签数在几十量级下并不严重；可作为后续优化且**不改数据模型** |

**含义**

- **引用方向使 A 成为唯一不需维护一致性的选项**：规则侧在「说自己的事」，标签侧在「说别人的事」。
- 反向查询（C4 删除确认的影响数、C3 孤立标签）由 `TagService` 遍历 `rules` 得出——**是它自己的职责范围**，不越界到 `RuleService` 的写入路径。
- **`tagIds` 是 rule 上的新字段**，`SyncState` 的穷尽校验若存在同类机制需同步（`PageRule` 属 sync 模型，见 F6 相关的模型族）。

## 4. 层内自检

- **与上游一致性**：G1 的「不影响执行」由 A-a 结构保证；C1 的 id 引用在 A4 得到包内落地、在 A6 得到存储方向；C2 的 trim 逐字节相等在 A-e 复用；C3 的「孤立标签须可见」由 A6 的反向查询支撑；C4/C5 的级联与撤销由 A-g 获得原子性；C7 的 chip 后备名（D2）在 A2 的 AST 上落地；C8 的 D1 由 A2 的纯模块承接。
- **矛盾检查**：
  - A4（包内无 id）vs C1（本机存 id）——**不矛盾**：id 是本机身份，包是一次性传输，`A4` 的导入重算即为桥接。
  - A5（可产生不自洽）vs C9（不兼容）——**不矛盾**：A5 使落盘文件**恒自洽**，故导入侧反而**更**严格。
  - A6（规则存 id）vs A4（包内存名）——**不矛盾**：两者是不同持久化边界，转换发生在导出与导入两侧。
- **术语**：「词汇表（vocabulary）」为本层新增术语（指包内根级 `tags: string[]`）；其余沿用 🔒 层新增术语。
- **未新增机制**：本层的三项「免费收益」均**复用既有能力**——级联原子性用 `mutateSync`（F1）、协议护栏用 `RULE_KEYS` 穷尽校验（F3）、撤销用 `UndoBar`（C5）。
