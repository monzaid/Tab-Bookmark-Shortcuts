## 0. 本层回溯修订的上游决策

本层发现一条**与 G2 直接冲突的硬边界**，并在决策过程中发生一次**范围扩大**，两者都已回写 Goal 文档。

| 上游 | 修订 |
|---|---|
| G1 | 「惰性数据」表述被取代：标签升格为**一等实体**（有独立管理界面、有生命周期）。**语义决策不变**（仍不影响匹配/优先级/启用）。同时新增「后续迭代有其他系统会用到 tag」⇒ 实体须定义在**共享层** |
| G3 | 追加第三处入口：**独立标签管理界面**（标签自身的增删改查） |

### 冲突卡：G2 的 300 条 vs 单条目 8KB

| 事实 | 出处 |
|---|---|
| 整个配置存于**一个** sync key | `storage-repository.ts:37` `const SYNC_KEY = 'syncState'` |
| 写入为整块 `set('sync', { syncState: updated })` | 同上 `:435` |
| 超限被分类为**可预期**错误并给文案 | 同上 `:467-472` |
| 只有 **data URI 图标**被卸载到 local（阈值 6KB） | 同上 `:71`；`offloadLargeIcons` |

**算术**：单条不含标题的 `PageRule` ≈ 170–200B；`QUOTA_BYTES_PER_ITEM = 8192` ⇒ **≈40 条**。加标签后（A 方案每条 +35B）300 条 = **约 10KB 额外**，单独即超限。

**裁决（A + C）**：300 条作为**界面设计目标**（不承担容量承诺，容量问题单独立项）；但 `tags` 的**上限校验本次就做**——它是用户可无限增长的字段，无上限等于把可复现的写入失败留给用户。**明确拒绝**「拆 key 突破 8KB」：会破坏「单条目原子写 + `configVersion` 乐观锁」这一现有一致性基础，代价远超本次收益。

## 1. 决策记录

### C1 — 标签的存储编码与身份

**决策**：**B — 全局标签表 + 规则存 id。**

`SyncState.tags: TagDefinition[]`（`{ id, name, backgroundColor, textColor }`）；`PageRule.tagIds: string[]`。**标签名只存一份。**

> **⚠️ 回溯修订（2026-10-11，📐 Detail 层收尾）**
>
> 原决策写的是 `{ id, name }[]` —— **标签被当成只有名字**。用户补充「标签不只是有 name 属性，还有背景色、文字颜色等属性」，该建模因此**不完整**；实体属性集扩展为 `name + backgroundColor + textColor`。
>
> **形状来源**：与仓库既有的 recipe 图标约定**同形**（`PortableIcon` recipe 的 `bgColor`/`textColor`、`IconSource` template 的 `backgroundColor`/`textColor`），故渲染能力（`IconPreview` 的三件套：背景色 + 文字 + 文字色）可直接复用，而非再造一套颜色模型。
>
> **未被影响的部分**：身份仍是**名字**（C2 的 trim 逐字节相等）。颜色是**外观**，**不参与**「是否同一个标签」的判定——否则改一次颜色就会变成一个「新标签」，而引用它的规则集体断链。
>
> **协议侧后果**：A4 的根级表须同步扩展（见 🏗️ 层 A4 修订）。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 每条规则直接存标签名 | ① 重命名需**遍历改写所有规则**（用户需要管理界面，故重命名是必须正确的能力）；② 容量：300 条 × 35B ≈ 10KB 重复存名，而全局表 ≈1.2KB，**B 省一个数量级**；③ 无法表达「孤立标签」（不被任何规则引用却存在于标签体系中） |

> 修订记录：本决策先在「只有规则内标签」的前提下被建议为 A（理由是「悬空状态不可能存在」），用户选择 B 并给出**管理界面 + 跨系统复用**两项新要求后，A 的该项优势不成立（B 下悬空由 C4 的级联删除闭合），B 的两项收益转为**必需**。

**含义**

- **「重命名标签」进入本次范围**（id 不变 ⇒ 引用不断，这正是 B 的核心收益）。
- 删除标签 = 删除实体 + 清理引用（见 C4）。
- **两个标签名在对应**（父子规则 vs 标签）都不再自描述，导出协议必须**同时**携带标签表（→ 🏗️ 层）。
- 存 id 使「引用完整性」成为需要主动维护的性质（A 下不需要），由 C4 + D3 承担。

### C2 — 标签名的规范化与「同名」判定

**决策**：**B — 仅 trim 首尾空格，名称区分大小写。**

`Work` ≠ `work`，两者**都出现在候选里**。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 原样保存 | 保留 `work` 与 ` work ` 并存 ⇒ 真正的重复条目 |
| C. 大小写不敏感去重、保留首次写法 | 抹掉用户对排版意图的二次判断；且需定义「首次写法」的权威来源与冲撞时的拒绝语义 |
| D. 统一归一为小写 | 强行抹掉 `Work` / `API` / `TODO` 的排版意图，候选列表可读性下降 |

> **更正记录**：本层初稿把 A/B 的风险描述为「看起来相同、实际不同」（不可解释）。事实上 `Work` 与 `work` 在候选里**渲染形态不同**，用户可分辨，故该论据不成立。B 保留。

**含义**

- **唯一性判定 = trim 后逐字节相等**。`work` 与 ` work ` **必须拒绝**（否则是真正重复的条目）。
- 该规则在写入路径与导入路径**各校验一次**（同 `isFaviconWriteSafe` 须在 create/update 两处把门的先例）。

### C3 — 规模上限

**决策**：**每条规则 ≤ 8 个标签；标签名 ≤ 32 字符；标签总数不限。**

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| 含「总数 ≤100 / ≤200」的选项 | 拒绝对总数设限（用户明确选择不限） |

**含义**

- **标签名长度是唯一真正的字节预算入口**（长名字同时放大标签表与所有引用处的可读性成本），故必须保留。
- **每条规则 ≤8**：在 50–300 条规则、几十个标签下，按标签找规则的行为特征是**少量标签做粗分类**，8 已远超真实用法。
- **总数不限的后果（登记，不加功能）**：标签会自然累积，且被 ≥5 条规则使用的标签可能很少。由此把两件事从「可选」变为**必需**：
  1. 候选列表**必须可搜索**（已由 G5 的 chip 输入框满足）；
  2. 管理界面**必须能看见孤立标签**（不被任何规则引用）——否则会积累成永久盲区。
- 「总数不限」与「表达式不设上限」不矛盾：表达式是 UI 态、不落盘、不占字节预算；标签是持久化数据。

### C4 — 删除标签的语义

**决策**：**C4 = B — 级联移除 + 明确告知影响数。**

确认框报出「将被 N 条规则摘除」，确认后删除标签并从所有引用规则中移除。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 阻止删除 | 300 条规则下惩罚性：删一个标签要手工编辑 N 条规则，与「管理界面」的存在意义相反 |
| C. 软删除（归档） | 引入**第三态**（既非存在亦非不存在），每个读取标签处都要处理「归档中」分支；归档是独立特性 |
| D. 允许悬空引用 | 把「未知标签」的渲染分支常驻 UI，且筛选表达式需定义「引用未知物」的语义 |

**含义**

- 删除是**破坏性但可撤销**的操作（见 C5）。
- **O7「悬空谓词」由此闭合**：级联移除后，规则侧不会悬空。但**筛选表达式是 UI 态、比标签表活得更久**，其落点见 C6。

### C5 — 删除的撤销

**决策**：**B — 复用现有 `UndoBar`。**

生成**原子批量快照**（标签实体 + 被摘除的全部引用），5 秒内可一键恢复。快照内容由「一个字段的旧值」扩展为「标签 + N 条引用」。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 不要撤销 | 危害严格大于既有的 Clear：Clear 破坏**一个**字段值，删标签破坏**散落在 N 条规则上**的引用，而规则本身仍在、静默地不再被筛选命中——「东西还在但关系没了」最难被察觉 |
| C. 长时限（24h）兜底 | 需一条持久化通道与清理/过期语义，把后悔药变成存储特性，超出「管理界面增删改查」范围 |

**含义**

- **沿用既有 `g2` 裁决**：`Confirm` 关闭 → 提交 → **再**弹 `UndoBar`，串行不并行。
- 无新机制：`DT9/IMP-6` 的泛化原子快照已具备该能力。

### C6 — 表达式不完整 / 为空时的行为

**决策**：**A — 视为「未筛选」，显示全部规则 + 框旁一行轻提示。**

空表达式与此相同。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| B. 只应用已完整部分（`work AND` 按 `work`） | 最糟：让 `AND` 成为**看起来生效、实际被忽略**的控件——这类特性最易失信 |
| C. 冻结上一次有效结果 | 半成品是正常输入路径的一部分，惩罚它会让人每次点选都看到列表冻结 |
| D. 清空列表并报错 | 把「编辑到一半」惩罚成「什么都看不见」 |

**含义**

- **确定性规则**：**只有解析成功的表达式才作用于列表**；其余一切（空、半成品、括号未闭合）一律退化为「未筛选」。
- 无错误面：`filters = parsed ? filterBy(parsed) : ALL`。

### C7 — 表达式引用的标签被删除 / 重命名

**决策**：**C — 保留 chip，整个表达式暂停生效 + 命名式提示。**

提示文案形如「表达式中的 tag x 已经被删除，暂未筛选，请手动调整表达式」。

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| A. 自动摘除 chip 并重新规范化 | 会让用户**已构建的筛选条件被静默改写**；规范化后用户看到的是一个自己没写过的表达式 |
| B. 保留 chip 且仍可求值（该谓词恒假） | `work AND <已删除>` 使列表静默变空，而表达式**语法上完全正常**——最难排查的「明明有规则却筛不出来」 |
| D. 清空整个表达式 | 删一个不相关的标签会清掉用户全部筛选条件，破坏性最强 |

**含义**

- ⚠️ **推导出硬约束 D2**：chip 必须**自带「插入时的名字」作为显示后备**。实体已删 ⇒ 表里查不到名字，但提示要**点名**该标签。显示优先级：**活表名字**（重命名自动跟随）→ **后备名**（已删时）。这同时使 C 的提示成为可能，且**无需墓碑记录**。
- **重命名不受影响**，且这正是 C1 的收益：id 不变 ⇒ 引用不断 ⇒ chip 自动显示新名字。

### C8 — 规模上限（表达式）

**决策**：**A — 不设上限。**

**被否决的替代**

| 选项 | 否决理由 |
|---|---|
| B. 软上限（提示复杂） | 「看起来有约束、实际没有」：问题（不可读、易误删）在构造过程中已产生 |
| C. 硬上限（16 谓词 / 4 层嵌套） | 被拒绝（用户选择完全信任） |
| D. 硬上限 + 引导 | 同上；且在越界瞬间给「如何改造你的思维」的建议成本高且居高临下 |

**含义**

- ⚠️ **推导出硬约束 D1**：**解析与求值不得因输入深度而崩溃**，须为**迭代实现**（或内部深度保护），不得使用朴素递归下降。理由：表达式一旦被持久化（或来自被破坏的存档），深嵌套即可产生；**爆栈的后果是设置页白屏，而非提示错误**。
- 该约束是**实现层不变量**，不是 UI 上限——用户侧确实没有上限。

### C9 — 持久化与兼容姿态

**决策**：**不承担向后兼容**（当前项目未上线，处于开发阶段）。

沿用 import-export 迭代 G1 的同一立场（该迭代已记录「用户明确处于开发阶段，无历史包需要兼容」）。

**含义**

- ① **本机读取：宽容补齐**（措辞经 2026-10-11 修订，见下方「语义澄清」）——`migrateSyncState` 对缺 `tags` / `tagIds` 按 `?? []` 补齐（与其他顶层字段同形），**不写迁移分支**；
- ② 导入包的标签字段**必填**，缺失即校验失败（**严格性只施加于导入包**）；
- ③ 筛选表达式**不持久化**（每次打开重置为空）——它是 UI 态，不进入存档协议；
- ④ 由此**「引用的标签已不存在」不可能来自存档**，只可能来自**本次会话内的删除**——即 C7 已处理的场景。**不需要第二份处理逻辑。**

> ### ⚠️ 语义澄清（2026-10-11，计划审查回溯）
>
> 原 ① 写作「存档缺 `tags` / `tagIds` ⇒ **视为损坏并拒绝**」。该措辞**与仓库既有形态冲突**，且与 ② 混为一谈，故修订为「① 宽容 / ② 严格」的分层。
>
> **冲突证据**：`storage-repository.ts:252-261` 的 `migrateSyncState` 对**每一个**顶层字段都用 `??` 兜底：
>
> ```ts
> configVersion: state.configVersion ?? 0,
> matchSettings: state.matchSettings ?? DEFAULT_MATCH_SETTINGS,
> switchDirection: state.switchDirection ?? 'next',
> autoBindGlobal: state.autoBindGlobal ?? true,
> slots: state.slots ?? [],
> rules: state.rules ?? [],
> ```
>
> 且它**不做规则级深规范化**（`rules` 原样透传）⇒ 旧存档里缺 `tagIds` 的规则在运行时是 `undefined`，而 TS 声称其为 `string[]`——**类型谎言**，必须补 `[]` 或按 ① 拒绝。
>
> **「不兼容」的准确定义**：C9 要防的是**迁移分支**（版本嗅探、形状试探、`configVersion` 因读取而变），`?? []` **两条都不沾**——它是既有的统一形态，而非迁移代码。因此：
>
> | 边界 | 姿态 |
> |---|---|
> | 本机存档读取 | **宽容**（顶层 `?? []` + 规则级补 `tagIds: []`）——与既有 6 个字段同形 |
> | 导入包校验 | **严格**（标签字段必填，缺失即失败） |
>
> **不影响 ④**：宽容补齐只处理「字段不存在」，不处理「引用了不存在的标签」——后者仍只可能来自会话内删除（C7）。

  - C3（标签有上限）vs C8（表达式无上限）——**不矛盾**，已说明：前者是持久化数据，后者是 UI 态。
  - C9（不兼容）vs C7（处理已删除标签）——**不矛盾**：C7 的场景来自会话内删除，非存档。
- **术语**：「标签（tag）」「标签表」「谓词（predicate）」「表达式（expression）」「chip」为本次新增术语，最终拼写与文案在 📐 Detail 层定稿。
